# Lean machine-audit contract

This document describes the repository's current executable Lean checks. It is
a living description of the audit contract enforced by CI, not an immutable
paper-correspondence record and not a claim that every formalization has
received human review.

The authoritative result for a particular revision is its passing CI run.
Historical human and AI-assisted source-comparison evidence is maintained
separately under [`AuditRecords/`](AuditRecords/).

## What is checked

The machine audit has four distinct layers.

### 1. Kernel build

`lake build` elaborates and compiles the public `GenLimit` umbrella. The
umbrella imports Core, all numbered paper developments, and the explicit bridge
layer. Lean's kernel checks every proof term needed by those imports.

The separate `Examples` library is compiled by `lake build Examples`. It is
kept outside the public `GenLimit.lean` dependency graph so that examples are
downstream clients rather than library dependencies.

### 2. Generated registry audit

[`RegistryAudit.lean`](RegistryAudit.lean) is generated by
[`../scripts/build_registry.py`](../scripts/build_registry.py). For every Lean
declaration directly linked from the claim registry, it checks:

- that the declaration resolves in the compiled Lean environment;
- that Lean reports the expected defining module;
- that its transitive logical dependencies are a subset of
  `propext`, `Classical.choice`, and `Quot.sound`.

The current generated file contains **550 declaration checks** associated with
the registry's **405 claims across 30 paper entries**. A source claim with no
formalized Lean component has no Lean declaration to check; its absence remains
explicit in the claim card.

The registry builder also enforces exact agreement between the 30 paper
umbrellas imported by `GenLimit.lean` and the registry's paper entries. This
prevents a new paper umbrella from silently falling outside the generated
claim-level audit inventory.

`RegistryAudit.lean` is generated output and must not be edited by hand.

### 3. Curated regression probes

[`Audit.lean`](Audit.lean) is a hand-maintained regression suite for selected
main results and important helper declarations. It currently contains:

- **112 exact-profile checks**, requiring precisely the three allowed logical
  principles;
- **479 allowlist checks**, permitting any subset of those principles;
- **591 probes in total**.

These probes include useful declarations that are not direct paper-claim links.
Conversely, this curated list is not intended to enumerate every current paper
or every registered declaration. Exhaustive claim-linked coverage belongs to
`RegistryAudit.lean`.

The exact-profile checks are deliberately stronger regressions: they fail if a
declaration's dependency profile changes in either direction. The ordinary
allowlist checks fail only when a dependency outside the project policy
appears.

### 4. Source and generated-artifact checks

CI additionally:

- scans project Lean sources for `sorry`, `admit`, `sorryAx`, or a
  project-defined `axiom`;
- validates the claim registry and all generated claim projections;
- rebuilds and compares the declaration-level index;
- checks human-audit applicability fingerprints;
- verifies the SHA-256 manifests for preserved external audit evidence.

The declaration index currently contains 10,340 public project declarations.
It is a retrieval index, not a substitute for kernel checking or
paper-correspondence review.

## One local command for both Lean audit layers

After Lake dependencies and the library build are available, run from the
repository root:

```bash
scripts/check_lean_audit.sh
```

or from `GenLimitLean/`:

```bash
../scripts/check_lean_audit.sh
```

The script runs, in order:

```bash
lake env lean RegistryAudit.lean
lake env lean Audit.lean
```

It exits unsuccessfully as soon as either layer fails. CI uses the same script,
so the documented local entry point and the hosted check cannot drift apart.

## Full reproducibility sequence

From the repository root:

```bash
python3 scripts/build_registry.py --check --require-umbrella-complete

cd GenLimitLean
lake exe cache get
lake build
lake build Examples
../scripts/check_lean_audit.sh

cd ..
python3 scripts/build_declaration_index.py --check
python3 scripts/check_audit_fingerprints.py
```

The generated declaration and registry checks are read-only in `--check`
mode. A source checkout whose generated files are stale will fail rather than
silently rewriting them.

## Scope boundaries

These machine checks establish that the recorded Lean declarations exist,
compile, have kernel-checked terms, and remain within the repository's stated
logical-dependency policy. They do **not** establish:

- that a Lean statement faithfully matches a paper statement;
- that a formalized algorithm matches source pseudocode;
- that proof structure corresponds to a paper proof;
- that semantic existence results are executable or satisfy an unstated
  complexity bound;
- that a source repair or counterexample has received human approval;
- that every non-private helper declaration is a stable public API.

PaperMaps and claim cards document statement boundaries and known gaps.
Human-review levels and their applicability fingerprints are recorded under
`AuditRecords/Human/`. The presence of a passing kernel or logical-dependency
audit must never be presented as a human paper-to-Lean audit.

## Why the two Lean files are separate

The generated and curated layers answer different questions:

| File | Question | Maintenance |
|---|---|---|
| `RegistryAudit.lean` | Does every Lean declaration claimed by the registry exist in the expected module and satisfy the allowlist? | Generated from registry metadata |
| `Audit.lean` | Have selected declarations retained deliberately monitored logical-dependency profiles? | Hand-maintained regression suite |

Copying all generated checks into the curated file would create two inventories
that can silently diverge. The unified script preserves a single local command
without duplicating ownership of the claim-linked declaration list.
